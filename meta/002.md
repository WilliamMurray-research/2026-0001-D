# Class‑Specific Metadata Extensions  
Each block below shows **only the additional fields** beyond the canonical schema.  
Your canonical schema remains the root.

---

## 1. **tmp — Template / Model / Scheme**
Purpose: structural definition, constraints, inheritance rules.

```yaml
class_extension:
  template_purpose: >
    Defines structure, constraints, and inheritance rules for documents of this class.
  allowed_inheritance_modes:
    - strict
    - loose
    - partial
  governs_classes:
    - tmp
    - charter
    - spec
    - protocol
    - risk
```

**Why:**  
Templates are governance primitives. They define the shape of the ecosystem.

---

## 2. **charter — Project / Initiative Charter**
Purpose: mandate, authority, boundaries, objectives.

```yaml
class_extension:
  mandate: >
    Statement of authority, purpose, and justification for the initiative.
  objectives:
    - "[Objective 1]"
    - "[Objective 2]"
  boundaries:
    in_scope: []
    out_of_scope: []
  stakeholders:
    primary: []
    secondary: []
  authority:
    sponsor: "[Name]"
    approver: "[Name]"
```

**Why:**  
Charters define *why* something exists and *who* owns it.

## 3. **spec — Specification (System / Component / Architecture)**
Purpose: technical definition, constraints, interfaces.

```yaml
class_extension:
  specification_type: "system"   # system | component | interface | architecture

    functional: []
```

## 4. **protocol — Process / Procedure / Method**
Purpose: operational rules, steps, triggers, conditions.

```yaml

  protocol_type: "operational"   # operational | safety | governance | technical
  triggers: []

    - id: 1
      action: "[Step description]"
    - id: 2
      action: "[Step description]"
  conditions:
    preconditions: []
    postconditions: []
  controls:
    monitoring: []

```

**Why:**  
Protocols define *how* something is executed.

---

## 5. **risk — Risk Assessment / Register / Control Set**
Purpose: identification, evaluation, mitigation.

```yaml
class_extension:
  risk_items:
    - id: "R-001"
      description: "[Risk description]"
      likelihood: "low"     # low | medium | high
      impact: "medium"      # low | medium | high
      rating: "medium"
      controls:
        existing: []
        proposed: []
      owner: "[Name]"
  methodology: "ISO 31000"
```

**Why:**  
Risk documents define *what can go wrong* and *how it is controlled*.

---

## 6. **wbs — Work Breakdown Structure**
Purpose: decomposition of work into governed units.

```yaml
class_extension:
  wbs_level: 1
  elements:
    - code: "1.0"
      name: "[Element]"
      description: "[Description]"
      children: []
  dependencies: []
  deliverables: []
```

**Why:**  
WBS documents define *the structure of work*.

# 🧩 How these extensions integrate  
Every document now has:

1. **Canonical metadata** (identity, classification, domain, inheritance, etc.)  
2. **Class‑specific extension** (the fields above)  
3. Optional **domain‑specific rules** (later layer)  

This gives you:

- deterministic structure  
- predictable parsing  
- inheritance enforcement  
- domain routing  
- graph‑based governance  
- symbolic‑neural rewrite compatibility  

This is exactly how governed ecosystems maintain coherence at scale.

Your classes form a **governance grammar**.  
Templates define syntax.  
Charters define mandate.  
Specs define semantics.  
Protocols define behaviour.  
Risk defines constraints.  
WBS defines decomposition.

Together, they form a *governed language* your OS‑substrate can manipulate.
