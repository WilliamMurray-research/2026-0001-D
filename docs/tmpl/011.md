## **1. Architectural Context & Problem Statement**

Document `010.md` defines the canonical metadata schema for governed assets across the repository. Automated parsers, static site generators, and indexers rely on valid YAML frontmatter blocks at line 1 of every markdown asset.

Currently, templates `001.md`, `002.md`, and `003.md` rely on inline Markdown key-value pairs (`**CLASSIFICATION**: D`) rather than valid YAML blocks. This creates parsing failures for automated ingest pipelines and violates the `010.md` specification.

---

## **2. Standard YAML Frontmatter Block Template**

Every template asset must begin at **Byte 0** with the following standardized block, customized per asset ID:

```yaml
---
reference: "2026-0001-D-tmpl-00X"
classification: "[A/B/C/D]"
title: "[Document Title]"
governance_domain: "[Domain from 010.md Taxonomy]"
type: "tmpl"
version: "0.X"
author: "William Murray"
role: "Research Architect"
date: "[YYYY-MM-DD]"
status: "[Draft/Stable/Superseded/Retired]"
scope: "Brief scope statement..."
primary_model: "2026-0001-D-tmpl-00X"
primary_model_url: "./tmpl/00X.md"

identity:
  year: 2026
  sequence: 0001
  class: "D"
  type: "tmpl"
  index: 00X
---

```

## **4. Validation Criteria**

To pass automated repository linting, updated files must satisfy:

* **YAML Syntax**: Validated via standard YAML linter (`yq` / `yamllint`). Block must sit between opening and closing `---` markers.
* **Domain Alignment**: Value for `governance_domain` must explicitly match one of the 12 categories from `010.md` Section 2.
* **Path Norms**: No hardcoded external URL prefixes (`[https://github.com/](https://github.com/)...`) within template schema pointers; relative local tree references only (`./` or `../`).

## 5. 

The specification focuses on `001`, `002`, and `003` because they are the immediate template assets that were reviewed and modified in your current workspace session.

However, **architecturally, this remediation applies to the entire repository**, not just those three files.

Here is why it should be treated as a systemic update across all assets:

### 1. Global Repository Standard (`010.md` as standard)

Document `010.md` was established as the **master scheme for machine-readable frontmatter across all governed documents**. Any markdown file in the repository—whether it is another template, an active governance document, an operational runbook, or a research doc—that lacks a compliant YAML block represents a schema violation.

### 2. Machine Ingestion Requirements

Automated tools, indexers, or CI/CD linting scripts do not filter by file index; they scan the entire directory tree. If only `001`–`003` get updated while `004`, `005`, or active docs in `/docs/governance/` remain in plain Markdown metadata, the parser will fail or produce partial records when building the repository graph.

### 3. Updated Scope for the Technical Doc

If you want the document to cover the full scope rather than just the three templates from this session, Section 1 and 3 of the technical document should be broadened from a single-file patch list to a repository-wide refactoring plan:

* **Phase 1 (Immediate Target)**: Standardize templates `001.md`, `002.md`, and `003.md`.
* **Phase 2 (Template Directory)**: Sweep all remaining files in `docs/tmpl/` (e.g., `004.md` onwards).
* **Phase 3 (Repository Core)**: Apply the YAML block retroactively across `/docs/governance`, `/docs/operations`, and root assets (`read-000`, `reg-000`).

Whenever you are ready to tackle it, the linter script or migration process can be run across the whole tree at once.
