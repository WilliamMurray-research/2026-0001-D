## Executive Summary  
The **2026 Naming & Directory Identification Model** defines a unified, ISO‑aligned system for naming, classifying, and organizing documents within a structured knowledge base. It introduces a compact, machine‑parseable identifier format and a comprehensive taxonomy of document types, enabling deterministic NLP extraction, PostgreSQL indexing, and Memgraph graph modelling.

The model is designed for environments requiring:

- strict classification integrity  
- predictable versioning  
- long‑term archival stability  
- automated metadata extraction  
- cross‑system interoperability  

This whitepaper explains the architectural rationale, operational implications, and governance principles behind the model, and demonstrates how it aligns with international standards bodies such as ISO, IEC, and ITU.

## 1. Introduction  
Knowledge systems often degrade under inconsistent naming, unclear classification, and ad‑hoc directory structures. The **2026 Naming & Directory Identification Model** addresses these issues by defining:

- a **directory identifier format**  
- a **document filename format**  
- a **classification system**  
- a **document type code taxonomy**  
- **inheritance rules**  
- **registry and export controls**  

The attached specification states:

> “This specification defines the directory identifier format, document filename format, classification rules, and document type codes which are used throughout the knowledge base.”

This whitepaper expands on those foundations and provides the architectural reasoning behind them.

## 2. Design Principles  
The model is built on five core principles.

### 2.1 Compactness  
Identifiers must remain short and readable.  
The model uses fixed‑width numeric fields and concise type codes such as `spec`, `arch`, `req`, `run`, `wp`.

### 2.2 Deterministic Parsing  
Every identifier component is machine‑extractable using simple regex patterns.  
This supports:

- NLP pipelines  
- automated indexing  
- metadata extraction  
- graph‑based reasoning  

### 2.3 ISO Alignment  
The structure mirrors ISO/IEC numbering conventions:

| ISO Concept | Model Equivalent |
|-------------|------------------|
| Standard family | Directory ID (`DDDD`) |
| Publication year | Year (`YYYY`) |
| Edition/version | Version (`VVV`) |
| Document part | Type code (`TYPE`) |
| Status | Classification (`C`) |

### 2.4 Classification Integrity  
The model enforces strict metadata‑exposure rules based on classification:

> “Items marked A (Air‑Gapped) or B (Confidential) must not expose sensitive operational metadata in public‑facing registry exports.”

This ensures operational metadata is never leaked.

### 2.5 Namespace Anchoring  
The directory identifier is the namespace root.  
Subdirectories are functional groupings only — they do not carry identifiers.

A 3‑digit sequential revision number.

## **B.2 General Terms**

### **B.2.1 Directory Identifier**  
A structured identifier in the format `YYYY-DDDD-C` representing a top‑level namespace.  
Defined in the spec as:

> “Each top‑level directory is assigned a unique identifier: `YYYY-DDDD-C`.”

### **B.2.2 Document Identifier**  
A structured filename in the format `YYYY-DDDD-C-TYPE-VVV.md` representing an atomic knowledge unit within a directory.

### **B.2.3 Namespace Root**  
The top‑level directory (`YYYY-DDDD-C`) that provides identity inheritance for all documents contained within it.

### **B.2.4 Inheritance**  
The rule that documents automatically adopt the directory’s year, directory ID, and classification.

> “All documents inherit the directory’s identifier.”

---

## **B.3 Identifier Components**

### **B.3.1 Year (YYYY)**  
The four‑digit year in which the directory and its documents were created.

### **B.3.2 Directory ID (DDDD)**  
A four‑digit sequential number representing the “standard family” or identity group.

### **B.3.3 Classification (C)**  
A single letter representing the security level of the directory and all documents within it.

### **B.3.4 Document Type (TYPE)**  
A short, fixed code describing the functional role of a document (e.g., `spec`, `arch`, `req`, `run`, `wp`).

### **B.3.5 Version (VVV)**  
A three‑digit sequential revision number representing the document’s edition.

---

## **B.4 Classification Levels**

### **B.4.1 Air‑Gapped (A)**  
Highest security level.  
Documents and directories must remain isolated from networked systems.  
No operational metadata may be exposed in public registry exports.

### **B.4.2 Confidential (B)**  
Sensitive internal material.  
Public registry exports must redact identifiers, version numbers, type codes, classification letters, and cross‑references.

### **B.4.3 Controlled (C)**  
Internal but non‑sensitive.  
Identifiers may be exported; operational metadata must be restricted.

### **B.4.4 Draft / Public‑Safe (D)**  
Lowest sensitivity.  
Full metadata export permitted.

---

## **B.5 Registry Concepts**

### **B.5.1 Registry Document (`reg`)**  
A document type used to track:

- next directory ID  
- next version number per type  
- classification changes  
- export restrictions  

### **B.5.2 Public‑Facing Registry Export**  
A sanitized version of the registry that omits or redacts metadata based on classification rules.

### **B.5.3 Operational Metadata**  
Metadata including identifiers, version numbers, type codes, classification letters, and cross‑references.  
Restricted for A and B classifications.

# **Annex C — Conformance & Compliance Requirements (Normative)**  
### Requirements for Implementing the 2026 Naming & Directory Identification Model

## **C.1 Purpose of This Annex**

## **C.2 Conformance Overview**  
To conform to the standard, an implementation must:

1. Use the identifier formats exactly as defined.  
2. Apply classification rules consistently.  
3. Use document type codes precisely as specified.  
4. Enforce inheritance rules without exception.  
5. Maintain registry integrity and classification‑based export controls.

These requirements are detailed in the following sections.

---

## **C.3 Identifier Format Compliance**

### **C.3.1 Directory Identifier Format**  
A compliant directory **must** use the format:

```
YYYY-DDDD-C
```

Where:

- `YYYY` is a valid four‑digit year.  
- `DDDD` is a four‑digit sequential directory ID.  
- `C` is one of the classification letters: A, B, C, or D.

### **C.3.2 Document Filename Format**  
A compliant document **must** use the format:

```
YYYY-DDDD-C-TYPE-VVV.md
```

Where:

- `TYPE` is one of the approved document type codes.  
- `VVV` is a three‑digit version number.  

### **C.3.3 Deterministic Parseability**  
All identifiers **must** be parseable using a deterministic pattern such as:

```
^(\d{4})-(\d{4})-([A-D])-([a-z]+)-(\d{3})\.md$
```

Any deviation from this pattern constitutes non‑conformance.

---

## **C.4 Classification Compliance**

### **C.4.1 Inheritance Requirement**  
All documents **must inherit** the classification of their parent directory.  
No document may override or redefine its classification.

### **C.4.2 Metadata Exposure Controls**  
Implementations **must** enforce the following:

- **A‑classified items**  
  - Must be fully omitted from public registry exports.  
  - Must not expose identifiers, versions, type codes, or relationships.

- **B‑classified items**  
  - Must be included only as redacted stubs.  
  - Must not expose operational metadata.

- **C‑classified items**  
  - May expose identifiers and type codes.  
  - Must not expose operational notes or dependency graphs.

- **D‑classified items**  
  - May expose full metadata.

These rules are mandatory.

---

## **C.5 Document Type Code Compliance**

### **C.5.1 Approved Codes Only**  
Implementations **must** use only the document type codes defined in the specification.  
Codes such as `spec`, `arch`, `req`, `run`, `wp`, `cnj`, `hyp`, `prf`, `mtg`, `note`, `reg`, `tmpl`, etc., are normative.

### **C.5.2 Functional Accuracy**  
Each document **must** use the type code that accurately reflects its functional role.  
For example:

- `run` **must** be used for environment‑specific operational steps.  
- `proc` **must** be used for general SOPs.  
- `cnj` **must** be used for mathematical conjectures.  
- `hyp` **must** be used for scientific hypotheses.

Incorrect classification constitutes non‑compliance.

### **C.5.3 Non‑Overlapping Semantics**  
Document type codes **must not** be used interchangeably.  
The distinctions defined in the specification (e.g., `cnj` vs `hyp`, `proc` vs `run`) are mandatory.

---

## **C.6 Versioning Compliance**

### **C.6.1 Sequential Versioning**  
Version numbers **must** increment sequentially:

```
001 → 002 → 003 → …
```

### **C.6.2 No Semantic Versioning in Filenames**  
Semantic versioning (e.g., `v1.2.3`) **must not** appear in filenames.  
It may appear inside the document body only.

### **C.6.3 Version Uniqueness**  
No two documents within the same directory and type may share the same version number.

---

**Mandatory Rules:**

- A‑classified items **must be fully omitted** from public registry exports.  
- No operational metadata may be exposed, including:  
  - directory identifiers  
  - version numbers  
  - document type codes  
  - classification letters  
  - cross‑references  
  - relationships  
- Internal exports **must** require explicit authorization.  
- A‑classified items **must never** appear in machine‑readable public formats (JSON, CSV, XML, API responses).

### **D.5.2 Confidential (B)**  
**Mandatory Rules:**

- B‑classified items **must be included only as redacted stubs** in public exports.  
- The following metadata **must be removed**:  
  - directory ID  
  - version number  
  - document type code  
  - classification letter  
  - cross‑references  
- Only the **existence** of the item may be disclosed.  
- Internal exports may include full metadata.

### **D.5.3 Controlled (C)**  
**Mandatory Rules:**

- Identifiers and type codes **may** be exported.  
- Operational metadata (notes, dependency graphs, relationships) **must not** be exported.  
- Public exports must not include:  
  - internal comments  
  - operational notes  
  - dependency graphs  
  - internal relationships  
- Internal exports may include full metadata.

### **D.5.4 Draft / Public‑Safe (D)**  
**Mandatory Rules:**

- Full metadata may be exported.  
- No redaction is required.  
- Public exports may include:  
  - directory ID  
  - version number  
  - type code  
  - classification  
  - relationships  
  - dependency graphs

# **Annex E — Document Type Code Rationale (Informative)**  
### Conceptual Foundations and Design Justification for the Document Type Taxonomy

---

## **E.1 Purpose of This Annex**  
This annex explains the **rationale**, **design intent**, and **functional boundaries** of each document type code defined in the 2026 Naming & Directory Identification Model.  
It clarifies why each code exists, how it should be used, and how it avoids semantic overlap with other codes.

This annex is **informative**, not normative.

---

## **E.2 Design Principles Behind the Taxonomy**

### **E.2.1 Functional Precision**  
Each type code represents a **function**, not a topic.  
This ensures documents are classified by their role in the system, not their subject matter.

### **E.2.2 Non‑Overlapping Semantics**  
Codes are designed to avoid ambiguity.  
Pairs such as `cnj` vs `hyp`, `proc` vs `run`, and `prj` vs `plan` are intentionally distinct.

### **E.2.3 Machine‑Parseability**  
Codes are short (3–5 letters), stable, and easy for NLP systems to extract.

### **E.2.4 ISO‑Aligned Part Structure**  
Each type code acts like an ISO “part” (e.g., ISO 12345‑1, ISO 12345‑2), enabling multi‑part standards within a directory.

### **E.2.5 Extensibility**  
The taxonomy is designed to expand without breaking existing classifications.

---

## **E.3 Rationale for Each Document Type Code**  
Grouped by functional domain.

---

## **E.3.1 Architecture & Engineering Codes**

### **arch** — Architecture  
Represents high‑level system design, topology, and structural diagrams.  
Rationale: Architecture documents define the system’s shape and constraints, forming the backbone of engineering governance.

### **adr** — Architecture Decision Record  
Captures significant architectural decisions, alternatives, and consequences.  
Rationale: ADRs provide traceability and justification for architectural evolution.

### **dig** — Diagram  
Standalone diagrams not embedded in an `arch` document.  
Rationale: Diagrams often need independent versioning and reuse.

### **schema** — Data Schema  
Defines database models, JSON schemas, and entity dictionaries.  
Rationale: Schemas are foundational artifacts requiring strict version control.

---

## **E.3.2 Governance & Standards Codes**

### **spec** — Specification  
Defines detailed technical or product requirements.  
Rationale: Specifications are authoritative and often normative.

### **std** — Standard  
Represents engineering standards, style guides, and design systems.  
Rationale: Standards govern consistency across systems and teams.

### **pol** — Policy  
Defines compliance rules and organizational governance.  
Rationale: Policies require strict classification and controlled distribution.

---

## **E.3.3 Projects & Planning Codes**

### **prj** — Project

Rationale: Projects need ongoing updates and clear separation from future planning.

### **plan** — Planning / Roadmap  
Forward‑looking timelines and strategic sequencing.  
Rationale: Plans are predictive, not descriptive, and must be distinguished from `prj`.

### **chtr** — Charter  
Defines project scope, objectives, and stakeholders.  
Rationale: Charters are foundational governance documents.

### **retro** — Retrospective  
Captures lessons learned and improvement actions.  
Rationale: Retrospectives support continuous improvement and auditability.

---

Rationale: SOPs must be stable, reusable, and environment‑agnostic.

Rationale: Runbooks differ from SOPs by being tied to specific systems.

Rationale: Maintenance requires predictable scheduling and strict versioning.

### **test** — Test / Validation  
Test plans and QA reports.  
Rationale: Testing requires strict traceability to requirements and specifications.

### **cnj** — Conjecture  
Formal mathematical proposition.  
Rationale: Conjectures must be distinguished from scientific hypotheses.

### **hyp** — Hypothesis  
Testable scientific assumption.  
Rationale: Hypotheses belong to empirical domains, not formal mathematics.

### **prf** — Proof  
Logical or mathematical proof.  
Rationale: Proofs validate conjectures or hypotheses and require strict versioning.

## **E.3.6 Administrative Codes**

Rationale: Meetings require structured documentation distinct from informal notes.

### **note** — Notes  
Informal, unstructured observations.  
Rationale: Notes must remain lightweight and flexible.

### **log** — Log / Audit  
Execution logs and audit trails.  
Rationale: Logs require immutability and strict classification.

Periodic analytical or business reports.

# **Annex I — Directory Lifecycle & Retirement SOP (Normative)**  
### Standard Operating Procedure for Directory Creation, Maintenance, Evolution, and Retirement

---

## **I.1 Purpose of This SOP**  
This annex defines the **complete lifecycle** of a directory (`YYYY-DDDD-C`) under the 2026 Naming & Directory Identification Model, including:

- creation  
- active maintenance  
- version evolution  
- classification changes  
- archival  
- retirement  
- deprecation  
- post‑retirement handling  

This annex is **normative**.

---

## **I.2 Lifecycle Overview**  
A directory progresses through the following lifecycle stages:

1. **Creation**  
2. **Active State**  
3. **Evolution**  
4. **Classification Adjustment**  
5. **Stabilization**  
6. **Deprecation**  
7. **Retirement**  
8. **Archival Preservation**

Each stage has mandatory requirements.

Explore related concepts:  
- **directory schema**  
- **registry structure**  
- **classification system**  

---

# **I.3 Stage 1 — Directory Creation (Normative)**  
Directory creation **must** follow Annex F (Directory Creation SOP).  
Key requirements:

- Identifier format: `YYYY-DDDD-C`  
- Subdirectories must be functional only  
- Initial registry file must be created  
- Global registry must be updated  
- Classification must be assigned and inherited  

Creation marks the beginning of the lifecycle.

---

# **I.4 Stage 2 — Active State (Normative)**  
A directory enters the **active state** immediately after creation.

### **I.4.1 Allowed Activities**
During active state, the following actions are permitted:

- creation of new documents  
- version updates  
- addition of new document types  
- updates to registry metadata  
- classification review  
- structural reorganization (functional only)

### **I.4.2 Mandatory Requirements**
- All documents must follow identifier format  
- All documents must inherit classification  
- Registry must remain up‑to‑date  
- Version numbers must increment sequentially  
- No semantic versioning in filenames  

---

# **I.5 Stage 3 — Evolution (Normative)**  
Evolution refers to structural or functional changes within the directory.

### **I.5.1 Evolution Triggers**
Evolution may occur due to:

- new document types  
- architectural changes  
- project expansion  
- new governance requirements  
- classification changes  

### **I.5.2 Evolution Requirements**
- Registry must record all changes  
- Version history must be preserved  
- Cross‑references must be updated  
- No identifier changes are permitted  
- No renaming of the directory is allowed  

Identifiers are immutable.

---

# **I.6 Stage 4 — Classification Adjustment (Normative)**  
A directory’s classification may change over time.

### **I.6.1 Allowed Classification Changes**
Classification may change:

- from D → C → B → A (tightening)  
- from A → B → C → D (loosening)  

### **I.6.2 Mandatory Requirements**
- All documents must inherit the new classification  
- Registry must record the classification change  
- Public registry exports must follow new rules  
- Operational metadata must be redacted or omitted based on new classification  

### **I.6.3 Prohibited Actions**
- Individual documents may not override classification  
- Classification may not be changed retroactively for previous directories  

---

# **I.7 Stage 5 — Stabilization (Normative)**  
A directory enters stabilization when:

- major documents are complete  
- version churn decreases  
- classification is unlikely to change  
- registry entries are stable  

### **I.7.1 Stabilization Requirements**
- Registry status must be updated to “Stable”  
- Version increments must slow or cease  
- No major structural changes should occur  
- Cross‑references must be finalized  

Stabilization is a precursor to deprecation.

---

# **I.8 Stage 6 — Deprecation (Normative)**  
Deprecation indicates that the directory is no longer actively maintained.

### **I.8.1 Deprecation Criteria**
A directory may be deprecated if:

- superseded by a newer directory  
- project or standard is discontinued  
- classification changes make it obsolete  
- content is no longer relevant  

### **I.8.2 Deprecation Requirements**
- Registry status must be updated to “Deprecated”  
- No new documents may be added  
- Only critical fixes may be applied  
- Version numbers may not increment except for fixes  
- Public registry exports must reflect deprecated status  

---

# **I.9 Stage 7 — Retirement (Normative)**  
Retirement is the final lifecycle stage.

### **I.9.1 Retirement Criteria**
A directory may be retired if:

- it has been deprecated for a defined period  
- it has been replaced by a newer directory  
- classification requires permanent removal  
- archival requirements mandate closure  

### **I.9.2 Retirement Requirements**
- Registry status must be updated to “Retired”  
- Directory must be locked (read‑only)  
- No further changes may be made  
- All documents must be frozen  
- Public registry exports must reflect retirement  
- A retirement notice must be added to the registry  

### **I.9.3 Retirement Notice Format**
```
retirement_notice:
  retired_on: YYYY-MM-DD
  reason: <text>
  superseded_by: <directory_id or null>
```

---

# **I.10 Stage 8 — Archival Preservation (Normative)**  
Retired directories must be preserved for historical and audit purposes.

### **I.10.1 Archival Requirements**
- Directory must be stored in an immutable archive  
- Registry must include archival metadata  
- Cross‑references must remain intact  
- Classification rules must still apply  
- Public exports must follow classification integrity  

### **I.10.2 Archival Metadata Format**
```
archival:
  location: <path or system>
  checksum: <hash>
  preserved_on: YYYY-MM-DD
  integrity_status: Verified
```

---

# **I.11 Directory Lifecycle Diagram (Informative)**  
A directory progresses through the following stages:

```
Creation → Active → Evolution → Classification Adjustment → Stabilization → Deprecation → Retirement → Archival
```

# **I.12 Compliance Requirements**

### **I.12.1 Mandatory Lifecycle Enforcement**
All lifecycle stages must be followed in order.

### **I.12.2 Registry Updates**
Registry must reflect lifecycle changes immediately.

### **I.12.3 Classification Integrity**
Classification rules must be enforced at every stage.

### **I.12.4 Identifier Immutability**
Identifiers must never change.

### **I.12.5 Archival Integrity**
Retired directories must be preserved without modification.

# **Annex J — Document Versioning Workflow (Normative)**  
### Standard Operating Procedure for Version Control Under the 2026 Naming & Directory Identification Model

---

## **J.1 Purpose of This SOP**  
This annex defines the **mandatory workflow** for versioning documents (`YYYY-DDDD-C-TYPE-VVV.md`) within a directory.  
It ensures:

- sequential versioning  
- identifier consistency  
- classification inheritance  
- registry accuracy  
- ISO‑aligned edition control  
- deterministic machine‑parseability  

This annex is **normative**.

---

## **J.2 Versioning Principles**

### **J.2.1 Sequential Versioning**  
Version numbers **must** increment sequentially:

```
001 → 002 → 003 → …
```

### **J.2.2 No Semantic Versioning in Filenames**  
Semantic versioning (e.g., `v1.2.3`) **must not** appear in filenames.  
Semantic versioning may appear **inside** the document body only.

### **J.2.3 Version Numbers Are Immutable**  
Once assigned, a version number **must never** be changed or reused.

### **J.2.4 Versioning Is Per Document Type**  
Each document type (`TYPE`) maintains its own version sequence.

Example:

```
spec: 001 → 002 → 003
note: 001 → 002
reg: 001 → 002
```

### **J.2.5 Versioning Is Directory‑Scoped**  
Version numbers do **not** carry across directories.  
Each directory (`YYYY-DDDD-C`) has its own version sequences.

---

## **J.3 Versioning Workflow Overview**

A compliant versioning workflow consists of:

1. **Version Trigger Identification**  
2. **Registry Lookup**  
3. **Version Number Assignment**  
4. **Document Creation or Update**  
5. **Registry Update**  
6. **Graph Relationship Update**  
7. **Validation**

Each step is defined below.

---

# **J.4 Step 1 — Version Trigger Identification (Normative)**

A version increment is triggered by:

- new document creation  
- modification of an existing document  
- correction of errors  
- classification changes  
- structural changes  
- content expansion  
- deprecation notices  
- retirement notices  

The following **do not** trigger a version increment:

- formatting changes  
- spelling corrections  
- metadata updates in the registry  
- directory‑level changes  

---

# **J.5 Step 2 — Registry Lookup (Normative)**

The registry file (`reg`) **must** be consulted to determine:

- the next version number for the document type  
- the version history  
- classification rules  
- export restrictions  

Example registry entry:

```
next_version_numbers:
  spec: 003
  note: 002
  reg: 002
```

---

# **J.6 Step 3 — Version Number Assignment (Normative)**

The version number **must** be assigned as:

```
VVV = next_version_numbers[TYPE]
```

Example:

```
TYPE = spec
next_version_numbers[spec] = 003
→ new version = 003
```

The version number **must** be padded to three digits.

---

# **J.7 Step 4 — Document Creation or Update (Normative)**

### **J.7.1 Filename Construction**
The filename **must** follow:

```
YYYY-DDDD-C-TYPE-VVV.md
```

Example:

```
2026-0001-D-spec-003.md
```

### **J.7.2 Classification Inheritance**
The document **must** inherit:

- directory year  
- directory ID  
- directory classification  

### **J.7.3 Version Header Update**
The document body **must** include:

- version number  
- version date  
- version status (Draft / Stable / Deprecated)  

---

# **J.8 Step 5 — Registry Update (Normative)**

The registry **must** be updated to reflect:

- new version number  
- updated version history  
- updated next version number  
- classification changes (if any)  
- document index updates  

Example update:

```
next_version_numbers:
  spec: 004

version_history:
  spec: [001, 002, 003]
```

---

# **J.9 Step 6 — Graph Relationship Update (Normative)**

Graph relationships **must** be updated:

### **J.9.1 Required Relationships**
- `VERSION_OF`  
- `TYPE`  
- `CLASSIFIED_AS`  
- `CONTAINS`  

### **J.9.2 Version Chain Integrity**
The new version **must** link to the previous version:

```
VERSION_OF: 2026-0001-D-spec-002.md
```

Broken version chains are a **critical validation failure**.

---

# **J.10 Step 7 — Validation (Normative)**

Validation **must** confirm:

- correct identifier format  
- correct version sequence  
- correct classification inheritance  
- correct registry updates  
- correct graph relationships  
- no semantic versioning in filename  
- no duplicate version numbers  
- no skipped version numbers  

Validation rules are defined in **Annex G**.

---

# **J.11 Versioning Rules by Classification Level**

### **J.11.1 Air‑Gapped (A)**  
- Versioning allowed internally  
- Public exports must omit all versions  
- Registry must store full version history internally  

### **J.11.2 Confidential (B)**  
- Versioning allowed  
- Public exports must redact version numbers  
- Internal registry must store full version history  

### **J.11.3 Controlled (C)**  
- Version numbers may be exported  
- Operational metadata must be redacted  

### **J.11.4 Draft / Public‑Safe (D)**  
- Full version metadata may be exported  
- Version chains must be visible  

---

# **J.12 Versioning Examples**

### **J.12.1 New Document**
```
TYPE = note
next_version_numbers[note] = 002
→ new file: 2026-0001-D-note-002.md
```

### **J.12.2 Updated Specification**
```
TYPE = spec
next_version_numbers[spec] = 003
→ new file: 2026-0001-D-spec-003.md
```

### **J.12.3 Deprecated Document**
```

next_version_numbers[arch] = 002
status: Deprecated
```

### **J.13.2 Identifier Immutability**
Identifiers must never change.

### **J.13.3 Version Chain Integrity**

# **L.3 Public Registry Export Structure (Normative)**

A compliant public registry export **must** contain the following sections:

1. **Header**  
2. **Directory Summary**  
3. **Document Index**  
4. **Classification‑Based Redaction**  
5. **Export Notes**

Each section is defined below.

---

# **L.4 Section 1 — Header (Mandatory)**

### **Required Fields**
| Field | Description |
|-------|-------------|
| `export_id` | Unique export identifier |
| `generated_on` | ISO 8601 timestamp |
| `generated_by` | System or author |
| `export_type` | Must be `"public"` |
| `model` | Naming model used |

### **Template**
```
export_id: <UUID>
generated_on: <YYYY-MM-DD>
generated_by: <system or author>
export_type: public
model: 2026 Naming & Directory Model
```

---

# **L.5 Section 2 — Directory Summary (Mandatory)**

### **Required Fields**
| Field | Description |
|-------|-------------|
| `directory_id` | Directory identifier (redacted for B) |
| `classification` | Classification letter (redacted for B) |
| `status` | Draft / Stable / Deprecated / Retired |
| `scope` | Directory scope |

### **Template**
```
directory:
  id: <directory_id or [REDACTED]>
  classification: <C or [REDACTED]>
  status: <Stable/Draft/Deprecated/Retired>
  scope: <text>
```

### **A‑Classified Handling**
This entire section **must be omitted** for A‑classified directories.

---

# **L.6 Section 3 — Document Index (Mandatory)**

Documents must be listed in deterministic order:

1. by document type  
2. then by version number  

### **Required Fields per Document**
| Field | A | B | C | D |
|-------|---|---|---|---|
| `doc_id` | omit | redact | full | full |
| `type` | omit | redact | full | full |
| `version` | omit | redact | redact | full |
| `title` | omit | full | full | full |
| `status` | omit | full | full | full |
| `classification` | omit | redact | full | full |

### **Template**
```
documents:
  - title: <document title>
    doc_id: <YYYY-DDDD-C-TYPE-VVV.md or [REDACTED]>
    type: <TYPE or [REDACTED]>
    version: <VVV or [REDACTED]>
    status: <Stable/Draft/Deprecated>
    classification: <C or [REDACTED]>
```

### **A‑Classified Handling**
A‑classified documents **must not appear** in the index.

---

# **L.7 Section 4 — Classification‑Based Redaction (Mandatory)**

### **Required Redaction Rules**
Public exports **must** apply:

- **A → omit entirely**  
- **B → redact operational metadata**  
- **C → redact operational metadata but allow identifiers**  
- **D → full metadata allowed**

### **Operational Metadata Includes**
- directory ID  
- version number  
- type code  
- classification letter  
- relationships  
- dependency graphs  
- internal notes  

### **Template**
```
redaction:
  A: omitted
  B:
    - directory_id
    - version
    - type
    - classification
    - relationships
  C:
    - relationships
    - internal_notes
  D: none
```

---

# **L.8 Section 5 — Export Notes (Mandatory)**

### **Required Fields**
| Field | Description |
|-------|-------------|
| `limitations` | Notes on redaction or omission |
| `classification_rules` | Summary of applied rules |
| `integrity_status` | Verified / Partial / Failed |

### **Template**
```
notes:
  limitations: >
    This export omits or redacts metadata based on classification rules.
  classification_rules:
    A: omitted
    B: redacted
    C: limited
    D: full
  integrity_status: Verified
```

# **L.10 Compliance Requirements**

### **L.10.1 Mandatory Template Usage**  
All public registry exports **must** use this template.

### **L.10.2 Deterministic Ordering**  
Documents must be ordered by type, then version.

### **L.10.3 Redaction Enforcement**  
Redaction rules must be applied exactly as defined.

### **L.10.4 Omission Enforcement**  
A‑classified items must be omitted entirely.

### **L.10.5 Machine‑Parseability**  
Exports must be parseable without heuristics.
