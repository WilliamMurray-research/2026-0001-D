# Decoupling Identity from Location in Governed Asset Schemas



### Architectural Invariants, Normalization, and Graph Topology in High-Integrity Technical Reference Systems

## Abstract

In large-scale knowledge bases, technical specifications, and enterprise relational databases, design paradigms often conflate an asset's physical storage path (present working directory or `pwd`) with its canonical reference identifier. This paper examines the systemic failure modes introduced by embedding dynamic filesystem hierarchy tokens into natural primary keys. We demonstrate how separating structural identity (`YYYY-DDDD-C-TYPE-NNN`) from positional location (`path`) preserves schema normalization, ensures deterministic regular expression parsing, maintains foreign key integrity across directory refactoring, and unlocks optimal graph-database traversal performance in heterogeneous computing environments.

---

## 1. Introduction & Theoretical Motivation

Modern technical documentation and asset metadata management demand deterministic parsing across disparate tools, including Natural Language Processing (NLP) pipelines, relational databases (PostgreSQL), and graph databases (Memgraph). A common architectural anti-pattern is the inclusion of contextual directory paths directly inside document identification strings—for instance, embedding `/docs/arch/` into a canonical identifier such as `2026-3001-C-docs-arch-001`.

While human intuition often favors encoding directory locations into file IDs for visual context, formal relational logic and system architecture dictate a strict separation between **Identity** (what an entity is) and **Location** (where an entity currently resides).

> **Core Design Invariant**
> 
> An entity's primary identifier must remain strictly invariant under structural refactoring, path migration, and storage reorganization. Location is an operational attribute; identity is a semantic property.

## 2. Systemic Failure Modes of Path-Encoded Identifiers

### 2.1 Failure of Deterministic Token Alignment in Positional Parsers

Governed asset schemas frequently rely on positional regex extraction to ingest incoming metadata into static database tables. A standard reference scheme enforces a strict token count:

$$\text{Identifier} = \text{Year} - \text{DirectoryID} - \text{Classification} - \text{TypeCode} - \text{Sequence}$$

Consider the regex parser specified in governed systems:

```regex
^(20\d{2})-([0-9]{4})-([ABCD])-([a-z]{2,10})-(\d{3})\.md$
```[cite: 2]

When path tokens (e.g., `docs`) are injected into the key structure, the delimiter count fluctuates dynamically[cite: 2]. The string `2026-3001-C-docs-arch-001` yields 6 tokens split by hyphens instead of 5[cite: 2]. Consequently, position-dependent parsers misalign token matches, pushing the document type code into an invalid register and causing automated ingestion pipelines to reject valid documents[cite: 2].

### 2.2 Relational Denormalization & Cascading Key Invalidation

In relational database design (3NF/BCNF), including the full or partial `pwd` within the primary key introduces a transitivity defect[cite: 2]. If a team moves a document from `docs/arch/` to `architecture/core/`, the path changes[cite: 2].

* **Path-Coupled Key:** Modifying the path forces a mutation of the primary key, triggering cascading updates across all referencing foreign key tables, audit logs, and external cross-references[cite: 2].
* **Decoupled Key:** The primary key (`2026-3001-C-arch-001`) remains static[cite: 2]. Only the mutable `path` attribute column in the database updates[cite: 2]:

```sql
UPDATE documents 
SET path = '2026-3001-C/architecture/core/001.md' 
WHERE reference = '2026-3001-C-arch-001';
```[cite: 2]

### 2.3 Foreign Key Constraint Failures in Standard Type Registries

System schemas enforce categorical integrity via lookup tables (e.g., `doc_types`)[cite: 2]. Compound path tags such as `docs-arch` fail lookup validations against approved enum sets, breaking database schema constraints[cite: 2]:

| Scheme Pattern | Sample Identifier | Type Lookup Value | Schema Validation |
|---|---|---|---|
| **Path-Coupled (Anti-Pattern)** | `2026-3001-C-docs-arch-001` | `docs-arch` | **FAIL** (FK Constraint Error)[cite: 2] |
| **Decoupled Invariant (Governed)** | `2026-3001-C-arch-001` | `arch` | **PASS** (Matches Standard Entry)[cite: 2] |

## 3. Graph-Theoretical Impact (Memgraph / Cypher)

In graph database architectures, encoding directory paths inside node identifiers compromises graph topology[cite: 2]. In Memgraph, relationships should be represented explicitly via typed edges rather than implicit string prefixes[cite: 2].

> **Graph Representation Standard**[cite: 2]  
> Directories and Documents must exist as distinct node labels linked by explicit `CONTAINS` or `REGISTERS` edges[cite: 2]:  
> `(d:Directory {directory_id: '3001'}) -[:CONTAINS]-> (doc:Document {reference: '2026-3001-C-arch-001'})`[cite: 2]

When path strings are embedded in node keys, graph traversals require expensive regular expression matching on node properties (e.g., `WHERE doc.id CONTAINS 'docs'`) rather than leveraging indexed pointer-hopping across graph edges ($O(1)$ localized traversal)[cite: 2].

## 4. Architectural Comparison

| Architectural Dimension | Path-Coupled Reference (`pwd` Included) | Decoupled Reference (Governed Standard) |
|---|---|---|
| **Entity Definition** | Identity conflated with physical filesystem location[cite: 2]. | Pure, immutable semantic identity[cite: 2]. |
| **Folder Refactoring** | Breaks IDs, foreign keys, and cross-document links[cite: 2]. | Zero impact on keys; simple metadata update[cite: 2]. |
| **Parsing Complexity** | Variable-length token splitting; error-prone[cite: 2]. | Fixed-position, single-pass Regex matching[cite: 2]. |
| **Graph Optimization** | Requires string scan operations over node keys[cite: 2]. | Native edge traversal using pointer indexes[cite: 2]. |
| **Database Normalization** | Violates 3NF/BCNF due to mutable key components[cite: 2]. | Fully normalized 3NF relational schema[cite: 2]. |

## 5. Conclusion

Decoupling an asset's identity from its filesystem location is a fundamental requirement for scalable knowledge architecture[cite: 2]. By strictly maintaining reference identifiers as `YYYY-DDDD-C-TYPE-NNN` while storing filesystem locations in a dedicated `path` attribute, technical systems achieve high resilience against refactoring, guarantee deterministic parsing across heterogeneous execution environments, and optimize graph database performance[cite: 2].
