## Purpose

This specification defines the:
1. Directory identifier format  
2. Document filename format  
3. Classification rules and export restrictions  
4. Document status vocabulary  
5. Document type codes  
6. Versioning and inheritance rules (header‑only)  
7. Reclassification and deprecation procedures  
8. NLP, database, and graph modelling guidance  

The system ensures short, stable, machine‑parseable identifiers that support NLP extraction, PostgreSQL indexing, and Memgraph graph modelling.



---

## 1. Directory Identifier Format

Each top‑level directory is assigned a unique identifier:

```
YYYY-DDDD-C
```

* **YYYY** – Year of directory creation  
* **DDDD** – 4‑digit sequential directory ID (globally unique across all years; does not reset per year). Range: `0001–9999`.  
* **C** – Classification letter (`A`–`D`) as defined in *Classification Levels* below.

> Example  
> ```
> 2026-1234-D
> ```



---

## 2. Document Filename Format

All documents inside a directory inherit its identifier. Filenames follow:

```
YYYY-DDDD-C-TYPE-NNN.md
```

Where:

| Component | Meaning |
|---|---|
| `YYYY` | Year (same as directory) |
| `DDDD` | Directory ID (same as directory) |
| `C` | Classification letter (same as directory) |
| `TYPE` | Document type code (always lowercase; must appear in the approved list; 2–10 characters) |
| `NNN` | **3‑digit stable sequence number** of that *document type* within the directory (`spec-001`, `req-002`, …). The sequence does **not** change when a new version is created. It is the “identity” of the document family. |

> Example  
> ```
> 2026-1234-D-spec-001.md
> ```

The file name is *authoritative* for the identity; the `Version:` header field (see Section 8) records only the semantic version for the current revision.

## **2.1 Lifecycle Code (First‑Digit of `DDDD`)**

The **first digit** of the directory identifier (`DDDD`) encodes the project’s **lifecycle domain** within the governed UOA ecosystem. This digit provides a stable, machine‑parseable semantic anchor for NLP extraction, PostgreSQL indexing, Memgraph graph modelling, and programme‑level governance. It ensures that every directory is structurally and semantically aligned with its correct phase in the research‑to‑operations pipeline.

Lifecycle codes are defined as follows:

| First Digit | Domain | Meaning |
|------------|--------|---------|
| **0** | **Governance** | Standards enforcement, structural invariants, compliance artefacts, programme‑level governance surfaces. |
| **1** | **Pure R&D** | Foundational research, theoretical development, unconstrained ideation, exploratory prototypes. |
| **2** | **Applied R&D** | Structured engineering research, domain‑specific application of theoretical constructs, early‑stage systems modelling. |
| **3** | **Commercial R&D** | Market‑aligned development, feasibility studies, pre‑product engineering, commercial viability analysis. |
| **4** | **Product** | Production‑grade systems, governed artefacts, stable releases, compliance‑aligned deliverables. |
| **5** | **Deployment / Integration** | Installation, environment adaptation, integration into operational contexts, initial operational capability. |
| **6** | **Maintenance / Sustainment** | Updates, patches, lifecycle extension, refactoring, long‑arc stewardship of deployed systems. |
| **7** | **Runtime & Monitoring** | Observability, telemetry, runtime invariants, monitoring dashboards, stability and behaviour under load. |
| **8** | **Custodial Oversight** | Fiduciary‑aligned stewardship, corpus protection, reclassification authority, long‑arc custodial obligations. |
| **9** | **Operations** | Resourcing, budgeting, staffing, organisational logistics, programme‑level operational continuity. |

### **Lifecycle Code Properties**

- The lifecycle code is **authoritative** for the directory’s role in the programme.  
- It is **immutable**; lifecycle reclassification requires the formal procedure defined in Section 5.  
- It is **machine‑parseable**, enabling deterministic ingestion pipelines across NLP, SQL, and graph‑model layers.  
- It provides a **semantic anchor** for the Unified Asset Registry and the Knowledge Layer, supporting lifecycle‑aware provenance tracking, dependency modelling, and structural governance.

### **Example**

A directory beginning with:

```
2026-7123-D
```

is interpreted as:

- **2026** → year of creation  
- **7***123* → runtime‑phase directory  
- **D** → unrestricted classification  

All documents within this directory inherit this lifecycle domain via the shared identifier prefix.

## 3. Classification Levels

Classification governs how metadata may be stored, exported, or exposed. Documents inherit the classification of their parent directory.

| Letter | Level | Description |
|---|---|---|
| **A** | Air‑Gapped | Highest security. Items remain isolated from networked systems. Public‑facing registry exports must exclude all operational metadata (identifiers, relationships, version history). |
| **B** | Confidential | Sensitive internal material. Public‑facing exports redact all operational metadata: directory identifiers, version numbers, document type codes, classification letters, and cross‑references. Only the existence of the item may be disclosed. |
| **C** | Controlled | Internal but non‑sensitive. Registry exports may include identifiers and type codes, but must not include internal operational notes or dependency graphs. |
| **D** | Unrestricted | Default for working documents. No access restrictions. Full registry metadata may be exported, including identifiers, type codes, version numbers, and relationships. |

> **Registry Export Rules**

| Classification | Export Behaviour |
|---|---|
| A | Fully omitted |
| B | Included as redacted stubs only |
| C | Included with limited metadata (identifiers and type codes; no operational notes or dependency graphs) |
| D | Fully included |

## 4. Document Status Vocabulary

Every document must carry one of the following status values in its header. Status is independent of classification and version number.

| Status | Meaning |
|---|---|
| **Draft** | Work in progress; not approved for use. Content may change without notice. |
| **Stable** | Approved and current. The authoritative version. Only one `Stable` per document type within a directory may exist at any time. |
| **Superseded** | Replaced by a named successor document. The successor’s reference must be recorded in the header as `Superseded‑By: YYYY-DDDD-C-TYPE-NNN`. Retained for lineage and audit. |
| **Retired** | Withdrawn from active use with no successor. Retained for reference and audit only; not to be cited as authoritative. |

> **Note** – The database column `status` is restricted to the four values above.



---

## 5. Reclassification Procedure

When a document or directory must change classification level:

1. **Create** a new directory with the target classification letter and the next available `DDDD` identifier.  
2. **Copy** the document into the new directory. The document receives a new reference reflecting the new directory (`YYYY‑DDDD‑C`) and begins at sequence `001`.  
3. **Mark** the original document status as `Superseded`, recording the new document reference in the header as `Superseded‑By: YYYY-DDDD-C-TYPE-001`.  
4. **Update** the registry to reflect the reclassification, the new identifier, and the lineage relationship (`RECLASSIFIED_FROM` edge in the graph model).

Documents cannot be reclassified in place. The directory classification is the authoritative source; document classification must always match its parent directory.



---

## 6. Deprecation and Deletion

Documents are never deleted from the knowledge base. Instead:

* Set `Status: Superseded` and record `Superseded‑By: YYYY-DDDD-C-TYPE-NNN` in the header when a successor document exists.  
* Set `Status: Retired` when a document is withdrawn with no successor.  
* The registry must reflect the status change.  
* Superseded and retired documents are excluded from default registry exports but remain queryable.

## Document Type Codes

Document type codes are short, fixed identifiers describing the **function** of a document. Codes are always lowercase (2–10 characters). These codes are stable and non-overlapping.

| Tag | Document Type | Description / Usage |
| --- | --- | --- |
| **`adr`** | Architecture Decision Record | Documents significant architectural choices, context, and consequences. |
| **`agmt`** | Agreement / Contract | Legal or formal business agreements and contracts. |
| **`api`** | API Reference | Interface specifications, endpoint definitions, and payload schemas. |
| **`arch`** | Architecture | High-level system design, topology, and structural diagrams. |
| **`chtr`** | Project Charter | Formal document defining scope, objectives, and stakeholders. |
| **`cnj`** | Conjecture | Proposed unproven mathematical conjecture (e.g. "Collatz conjecture"). Distinct from `hyp`: use for formal mathematical propositions, not scientific assumptions. |
| **`config`** | Configuration | System parameters, environment configs, and feature flag definitions. |
| **`dig`** | Diagram | Standalone visual artifacts such as ERDs, flowcharts, or network maps not embedded in an `arch` document. |
| **`doc`** | General Document | Uncategorized standard documents or general written materials. |
| **`faq`** | Frequently Asked Questions | Compiled Q&A for common troubleshooting or general knowledge. |
| **`guide`** | User Guide / Manual | Step-by-step end-user instructions and usage manuals. Distinct from `ref`: use when the primary purpose is instruction, not lookup. |
| **`hyp`** | Hypothesis | Scientific hypothesis, experimental assumptions, or empirical proposals. Distinct from `cnj`: use for testable, evidence-based claims, not formal mathematical propositions. |
| **`inc`** | Incident Report | Post-mortems, root-cause analyses, and incident summaries. |
| **`log`** | Log / Audit | Execution logs, security audit trails, and activity records. |
| **`maint`** | Maintenance | Scheduled maintenance plans, window procedures, and health checks. |
| **`mtg`** | Meeting Agenda / Minutes | Structured pre-meeting agendas or post-meeting minutes. Distinct from `note`: use when there is a formal agenda, attendee list, or action items. |
| **`note`** | Notes | Informal scratchpads, quick observations, and unstructured jottings without a formal agenda. |
| **`plan`** | Planning / Roadmap | Forward-looking strategic roadmaps, project timelines, and sprint plans. Distinct from `prj`: use for future-oriented scheduling and sequencing. |
| **`pol`** | Policy | Organizational rules, compliance guidelines, and security policies. |
| **`ppr`** | Paper | Philosophy, first principles, etc |
| **`prf`** | Proof | Logical or mathematical proofs confirming a hypothesis or conjecture. |
| **`prj`** | Project | Project overviews and status reports. Distinct from `plan`: use for current-state tracking and summaries, not forward-looking roadmaps. |
| **`proc`** | Process / SOP | Standard Operating Procedures and operational workflows describing *how* a process works. Distinct from `run`: use for general SOPs, not environment-specific operational steps. |
| **`read`** | README | Description of project and contents of subdirectories. |
| **`ref`** | Reference | Glossaries, cheat sheets, quick-reference cards, and lookup tables. Intentionally broad: use when the primary purpose is rapid lookup rather than instruction. |
| **`reg`** | Registry | Asset tracking, inventory logs, or component registries. |
| **`rel`** | Release Notes | Version changelogs, update summaries, and patch notes. |
| **`req`** | Requirements | Product (PRD) or business (BRD) requirements specifications. |
| **`retro`** | Retrospective | Sprint or project retrospectives capturing what went well, what didn't, and action items. |
| **`rfp`** | Request for Proposal / Quote | Procurement and vendor-selection documents soliciting bids or proposals. Distinct from `req` (internal requirements) and `agmt` (executed agreements). |
| **`rpt`** | Report | Periodic analytical or business reports such as weekly status updates, KPI dashboards, or audit summaries. Distinct from `prj` (project overviews) and `inc` (incident-specific). |
| **`run`** | Runbook | Operational step-by-step guides for specific environments covering deployment, recovery, and on-call procedures. Distinct from `proc`: use for environment-specific execution steps, not general SOPs. |
| **`schema`** | Data Schema | Database entity models, JSON schemas, or data dictionaries. |
| **`spec`** | Specification | Detailed technical or product specifications. |
| **`std`** | Standard | Engineering standards, style guides, and design systems. |
| **`test`** | Test / Validation | Test plans, test cases, and quality assurance reports. |
| **`tmpl`** | Template | Blank or reusable document skeletons intended to be filled in. Distinct from the instantiated document type they produce. |
| **`toc`** | Table of Contents | List of linked assets |
| **`tut`** | Tutorial | Educational walkthroughs and hands-on getting-started guides. |
| **`wp`** | Whitepaper | In-depth technical papers, research, or position statements. |

### Notes on Commonly Confused Pairs

| Pair | Distinction |
| --- | --- |
| `cnj` vs `hyp` | `cnj` = formal mathematical proposition; `hyp` = testable scientific assumption |
| `proc` vs `run` | `proc` = general SOP describing how a process works; `run` = environment-specific operational execution steps |
| `prj` vs `plan` | `prj` = current-state project overview and status; `plan` = forward-looking roadmap or timeline |
| `note` vs `mtg` | `note` = informal, unstructured; `mtg` = has a formal agenda, attendees, or action items |
| `req` vs `rfp` | `req` = internal requirements spec; `rfp` = external procurement solicitation |
| `ref` vs `guide` | `ref` = lookup-first (glossaries, cheat sheets); `guide` = instruction-first (step-by-step manuals) |

## 8. Version Numbering (Header‑Only)

The filename contains only the **stable sequence number** (`NNN`). The header field

```
Version: X.Y
```

is a *semantic* version that may follow MAJOR.MINOR or other conventions as required by the document’s domain. It is **not** tied to the file name and can change independently with each revision.

> Example  
> ```
> Version: 3.0   # Semantic – third major release, no patch
> ```

The `Version:` header value must match the semantic version recorded in the graph edge `VERSION_OF` (see Section 9). It is independent of the file name.



---

## 9. Inheritance Rules

1. All documents inherit the directory’s `YYYY`, `DDDD`, and `C`.  
2. Classification letter is shared between directory and all documents within it.  
3. Directory year and document year must match.  
4. Document type codes must appear in the approved list, be lowercase, and 2–10 characters.  
5. **Sequence numbers** increment per *document type* within a directory, not per document or per revision.  
6. Security restrictions apply uniformly to all items within a directory.  
7. Documents cannot carry a classification different from their parent directory. Reclassification requires a new directory.

## 10. NLP, Database, and Graph Considerations

### 10.1 NLP Extraction

The filename structure allows deterministic extraction of all structured fields.

Suggested regex:

```
^(20\d{2})-([0-9]{4})-([ABCD])-([a-z]{2,10})-(\d{3})\.md$
```

Capture groups: `(year)(directory_id)(classification)(doc_type)(sequence)`



### 10.2 PostgreSQL Schema

Requires PostgreSQL 12 or later (for `GENERATED ALWAYS AS … STORED` on `TSVECTOR`).

```sql
CREATE TABLE directories (
    directory_id   CHAR(4)      NOT NULL,
    year           CHAR(4)      NOT NULL,
    classification CHAR(1)      NOT NULL CHECK (classification IN ('A','B','C','D')),
    created_at     DATE         NOT NULL,
    PRIMARY KEY (year, directory_id)
);

CREATE TABLE doc_types (
    code           VARCHAR(10)  PRIMARY KEY,
    label          VARCHAR(100) NOT NULL
);

CREATE TABLE documents (
    id             SERIAL       PRIMARY KEY,
    year           CHAR(4)      NOT NULL,
    directory_id   CHAR(4)      NOT NULL,
    classification CHAR(1)      NOT NULL CHECK (classification IN ('A','B','C','D')),
    doc_type       VARCHAR(10)  NOT NULL REFERENCES doc_types (code),
    sequence        CHAR(3)      NOT NULL,                     -- stable identity
    status         VARCHAR(12)  NOT NULL CHECK (status IN ('Draft','Stable','Superseded','Retired')),
    superseded_by  TEXT         NULL,
    header_version TEXT         NOT NULL,                      -- semantic version in the document
    path           TEXT         NOT NULL,
    content        TEXT         NOT NULL,
    content_tsv    TSVECTOR     GENERATED ALWAYS AS (to_tsvector('english', content)) STORED,
    UNIQUE  (year, directory_id, doc_type, sequence),
    FOREIGN KEY (year, directory_id) REFERENCES directories (year, directory_id),
    FOREIGN KEY (doc_type)           REFERENCES doc_types   (code)
);

CREATE INDEX idx_documents_type    ON documents (doc_type);
CREATE INDEX idx_documents_status  ON documents (status);
CREATE INDEX idx_documents_tsv     ON documents USING GIN (content_tsv);
```



### 10.3 Memgraph Graph Model

**Nodes**

| Node | Properties |
|---|---|
| `Directory` | `directory_id`, `year`, `classification`, `created_at` |
| `Document` | `reference`, `year`, `directory_id`, `classification`, `doc_type`, `sequence`, `status`, `path`, `header_version` |
| `DocType` | `code`, `label` |
| `Classification` | `letter`, `level_name` |

**Edges**

| Edge | From → To | Meaning |
|---|---|---|
| `CONTAINS` | Directory → Document | Directory holds this document |
| `VERSION_OF` | Document → Document | This document is the *next revision* of another with the same identity (`YYYY‑DDDD‑C‑TYPE‑NNN`) but a higher `header_version`. The file name stays identical. |
| `TYPE` | Document → DocType | Document belongs to this type |
| `CLASSIFIED_AS` | Document → Classification | Document carries this classification |
| `SUPERSEDES` | Document → Document | This document replaces another document of a different identity (e.g. post‑reclassification successor) |
| `RECLASSIFIED_FROM` | Document → Document | This document originated from a reclassification of another; implies a `SUPERSEDES` edge also exists |

> **Edge usage note** –  
> * `VERSION_OF` connects revisions of the same document identity (`NNN`).  
> * `SUPERSEDES` connects documents of different identities where one replaces the other.  
> * A reclassified document carries both `SUPERSEDES` and `RECLASSIFIED_FROM` to the original.

## 11. Registry Compliance

All new directories and documents must follow this specification. Registry files must track:

* Next available directory ID (`DDDD`)  
* Next version number per document, per directory (i.e., next **sequence**)  
* Current status of each document  
* Classification of each directory and document  
* Export restrictions based on classification rules (see *Registry Export Rules*)  
* Reclassification lineage  
* Supersession relationships
