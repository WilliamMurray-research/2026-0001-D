---

## Purpose

This specification defines the:
1. Directory identifier format
2. Document filename format
3. Classification rules and export restrictions
4. Document status vocabulary
5. Document type codes
6. Version and inheritance rules
7. Reclassification and deprecation procedures
8. NLP, database, and graph modelling guidance

The system ensures short, stable, machine-parseable identifiers that support NLP extraction, PostgreSQL indexing, and Memgraph graph modelling.

---

## Directory Identifier Format

Each top-level directory is assigned a unique identifier:

```
YYYY-DDDD-C
```

Where:

- **YYYY** — Year of directory creation
- **DDDD** — 4-digit sequential directory ID, globally unique across all years (does not reset per year). Range: `0001–9999`.
- **C** — Classification letter (see Classification Levels below)

### Example

```
2026-1234-D
```

---

## Document Filename Format

All documents inside a directory inherit its identifier. Filenames follow:

```
YYYY-DDDD-C-TYPE-VVV.md
```

Where:

- **YYYY** — Year (same as directory)
- **DDDD** — Directory ID (same as directory)
- **C** — Classification letter (same as directory)
- **TYPE** — Document type code (always lowercase; must appear in the approved list)
- **VVV** — 3-digit version number (`001–999`)

### Example

```
2026-1234-D-spec-001.md
```

## Classification Levels

Classification governs how metadata may be stored, exported, or exposed. Documents inherit the classification of their parent directory.

| Letter | Level | Description |
| --- | --- | --- |
| **A** | Air-Gapped | Highest security. Items must remain isolated from networked systems. No public-facing registry exports may include any operational metadata — identifiers, relationships, or version history. |
| **B** | Confidential | Sensitive internal material. Public-facing exports must redact all operational metadata: directory identifiers, version numbers, document type codes, classification letters, and cross-references. Only the existence of the item may be disclosed. |
| **C** | Controlled | Internal but non-sensitive. Registry exports may include identifiers and type codes, but must not include internal operational notes or dependency graphs. |
| **P** | Public | Formally released and approved for public distribution. Full registry metadata may be exported, including identifiers, type codes, version numbers, and relationships. |
| **D** | Draft | Working documents not yet approved for release. Full internal metadata is visible within the system, but Draft documents must not be included in public-facing registry exports until reclassified to P. |

> **Note on D vs P:** `D` (Draft) and `P` (Public) are distinct states. A document is classified `D` while in progress and reclassified to `P` upon formal approval. Do not use `D` to mean "safe to publish."

### Registry Export Rules

When generating public-facing registry exports:

| Classification | Export Behaviour |
| --- | --- |
| **A** | Fully omitted |
| **B** | Included as redacted stubs only |
| **C** | Included with limited metadata (identifiers and type codes; no operational notes or dependency graphs) |
| **D** | Excluded from public exports; full metadata visible internally |
| **P** | Fully included |

## Document Status Vocabulary

Every document must carry one of the following status values in its header. Status is independent of classification and version number.

| Status | Meaning |
| --- | --- |
| **Draft** | Work in progress; not approved for use. |
| **Review** | Submitted for formal review; content frozen pending approval. |
| **Stable** | Approved and current. The authoritative version. |
| **Deprecated** | Superseded or withdrawn; retained for reference only. Not to be cited as authoritative. |
| **Superseded** | Replaced by a named successor document. The successor's reference must be recorded in the document header. |

Only one document version per type within a directory may hold `Stable` status at any time.

---

## Reclassification Procedure

When a document or directory must change classification level:

1. **Create a new directory** with the target classification letter and the next available `DDDD` identifier.
2. **Copy the document** into the new directory. The document receives a new reference reflecting the new directory (new `YYYY-DDDD-C`) and resets to version `001`.
3. **Mark the original** document status as `Superseded`, recording the new document reference in the header.
4. **Update the registry** to reflect the reclassification, the new identifier, and the lineage relationship (`RECLASSIFIED_FROM` edge in the graph model).

Documents cannot be reclassified in place. The directory classification is the authoritative source; document classification must match.

---

## Deprecation and Deletion

Documents are never deleted from the knowledge base. Instead:

- Set `Status: Deprecated` or `Status: Superseded` in the document header.
- If superseded, record the successor's document reference in the header as `Superseded-By: YYYY-DDDD-C-TYPE-VVV`.
- The registry must reflect the status change.
- Deprecated and superseded documents are excluded from default registry exports but remain queryable.

## Document Type Codes

Document type codes are short, fixed identifiers describing the **function** of a document. Codes are always lowercase. These codes are stable and non-overlapping.

| Tag | Document Type | Description / Usage |
| --- | --- | --- |
| **`adr`** | Architecture Decision Record | Documents significant architectural choices, context, and consequences. |
| **`agmt`** | Agreement / Contract | Legal or formal business agreements and contracts. |
| **`api`** | API Reference | Interface specifications, endpoint definitions, and payload schemas. |
| **`arch`** | Architecture | High-level system design, topology, and structural diagrams. |
| **`chtr`** | Project Charter | Formal document defining scope, objectives, and stakeholders. |
| **`cnj`** | Conjecture | Proposed unproven mathematical conjecture (e.g. "Collatz conjecture"). Distinct from `hyp`: use for formal mathematical propositions, not scientific assumptions. |
| **`config`** | Configuration | System parameters, environment configs, and feature flag definitions. |
| **`dig`** | Diagram | Standalone visual artifacts such as ERDs, flowcharts, or network maps not embedded in an `arch` document. |
| **`doc`** | General Document | Uncategorized standard documents or general written materials. |
| **`faq`** | Frequently Asked Questions | Compiled Q&A for common troubleshooting or general knowledge. |
| **`guide`** | User Guide / Manual | Step-by-step end-user instructions and usage manuals. Distinct from `ref`: use when the primary purpose is instruction, not lookup. |
| **`hyp`** | Hypothesis | Scientific hypothesis, experimental assumptions, or empirical proposals. Distinct from `cnj`: use for testable, evidence-based claims, not formal mathematical propositions. |
| **`inc`** | Incident Report | Post-mortems, root-cause analyses, and incident summaries. |
| **`log`** | Log / Audit | Execution logs, security audit trails, and activity records. |
| **`maint`** | Maintenance | Scheduled maintenance plans, window procedures, and health checks. |
| **`mtg`** | Meeting Agenda / Minutes | Structured pre-meeting agendas or post-meeting minutes. Distinct from `note`: use when there is a formal agenda, attendee list, or action items. |
| **`note`** | Notes | Informal scratchpads, quick observations, and unstructured jottings without a formal agenda. |
| **`plan`** | Planning / Roadmap | Forward-looking strategic roadmaps, project timelines, and sprint plans. Distinct from `prj`: use for future-oriented scheduling and sequencing. |
| **`pol`** | Policy | Organizational rules, compliance guidelines, and security policies. |
| **`prf`** | Proof | Logical or mathematical proofs confirming a hypothesis or conjecture. |
| **`prj`** | Project | Project overviews and status reports. Distinct from `plan`: use for current-state tracking and summaries, not forward-looking roadmaps. |
| **`proc`** | Process / SOP | Standard Operating Procedures and operational workflows describing *how* a process works. Distinct from `run`: use for general SOPs, not environment-specific operational steps. |
| **`ref`** | Reference | Glossaries, cheat sheets, quick-reference cards, and lookup tables. Intentionally broad: use when the primary purpose is rapid lookup rather than instruction. |
| **`reg`** | Registry | Asset tracking, inventory logs, or component registries. |
| **`rel`** | Release Notes | Version changelogs, update summaries, and patch notes. |
| **`req`** | Requirements | Product (PRD) or business (BRD) requirements specifications. |
| **`retro`** | Retrospective | Sprint or project retrospectives capturing what went well, what didn't, and action items. |
| **`rfp`** | Request for Proposal / Quote | Procurement and vendor-selection documents soliciting bids or proposals. Distinct from `req` (internal requirements) and `agmt` (executed agreements). |
| **`rpt`** | Report | Periodic analytical or business reports such as weekly status updates, KPI dashboards, or audit summaries. Distinct from `prj` (project overviews) and `inc` (incident-specific). |
| **`run`** | Runbook | Operational step-by-step guides for specific environments covering deployment, recovery, and on-call procedures. Distinct from `proc`: use for environment-specific execution steps, not general SOPs. |
| **`schema`** | Data Schema | Database entity models, JSON schemas, or data dictionaries. |
| **`spec`** | Specification | Detailed technical or product specifications. |
| **`std`** | Standard | Engineering standards, style guides, and design systems. |
| **`test`** | Test / Validation | Test plans, test cases, and quality assurance reports. |
| **`tmpl`** | Template | Blank or reusable document skeletons intended to be filled in. Distinct from the instantiated document type they produce. |
| **`tut`** | Tutorial | Educational walkthroughs and hands-on getting-started guides. |
| **`wp`** | Whitepaper | In-depth technical papers, research, or position statements. |

### Notes on Commonly Confused Pairs

| Pair | Distinction |
| --- | --- |
| `cnj` vs `hyp` | `cnj` = formal mathematical proposition; `hyp` = testable scientific assumption |
| `proc` vs `run` | `proc` = general SOP describing how a process works; `run` = environment-specific operational execution steps |
| `prj` vs `plan` | `prj` = current-state project overview and status; `plan` = forward-looking roadmap or timeline |
| `note` vs `mtg` | `note` = informal, unstructured; `mtg` = has a formal agenda, attendees, or action items |
| `req` vs `rfp` | `req` = internal requirements spec; `rfp` = external procurement solicitation |
| `ref` vs `guide` | `ref` = lookup-first (glossaries, cheat sheets); `guide` = instruction-first (step-by-step manuals) |

## Version Numbering

Version numbers are 3-digit sequential integers:

```
VVV = 001 → 002 → 003 → …
```

- Version numbers represent document revisions, not semantic versioning.
- Semantic versioning, if required, is stored inside the document body, not in the filename.
- The Technical Standard version in the document subtitle (e.g. `v2.0`) reflects the version of this specification itself and must match `VVV` expressed as a decimal (i.e. version `002` = `v2.0`).
- Version numbers are per-document and do not reset when classification changes; the new document created during reclassification begins at `001`.

---

## Inheritance Rules

1. All documents inherit the directory's `YYYY`, `DDDD`, and `C` identifier components.
2. Classification letter is shared between directory and all documents within it.
3. Directory year and document year must match.
4. Document type codes must appear in the approved list and be lowercase.
5. Version numbers increment per document, not per directory.
6. Security restrictions apply uniformly to all items within a directory.
7. Documents cannot carry a classification different from their parent directory. Reclassification requires a new directory.

## NLP, Database, and Graph Considerations

### NLP Extraction

The filename structure allows deterministic extraction of:

- Year
- Directory ID
- Classification
- Document type
- Version

Suggested regex: `^(\d{4})-(\d{4})-([ABCDP])-([a-z]+)-(\d{3})\.md$`

### PostgreSQL Schema

```sql
CREATE TABLE directories (
    directory_id   CHAR(4)      NOT NULL,
    year           CHAR(4)      NOT NULL,
    classification CHAR(1)      NOT NULL CHECK (classification IN ('A','B','C','D','P')),
    created_at     DATE         NOT NULL,
    PRIMARY KEY (year, directory_id)
);

CREATE TABLE documents (
    id             SERIAL       PRIMARY KEY,
    year           CHAR(4)      NOT NULL,
    directory_id   CHAR(4)      NOT NULL,
    classification CHAR(1)      NOT NULL CHECK (classification IN ('A','B','C','D','P')),
    doc_type       VARCHAR(10)  NOT NULL,
    version        CHAR(3)      NOT NULL,
    status         VARCHAR(12)  NOT NULL CHECK (status IN ('Draft','Review','Stable','Deprecated','Superseded')),
    superseded_by  VARCHAR(50)  NULL,
    path           TEXT         NOT NULL,
    content        TEXT         NOT NULL,
    content_tsv    TSVECTOR     GENERATED ALWAYS AS (to_tsvector('english', content)) STORED,
    FOREIGN KEY (year, directory_id) REFERENCES directories (year, directory_id)
);

CREATE INDEX idx_documents_type    ON documents (doc_type);
CREATE INDEX idx_documents_status  ON documents (status);
CREATE INDEX idx_documents_tsv     ON documents USING GIN (content_tsv);
```

### Memgraph Graph Model

**Nodes**

| Node | Properties |
| --- | --- |
| `Directory` | `directory_id`, `year`, `classification`, `created_at` |
| `Document` | `reference`, `year`, `directory_id`, `classification`, `doc_type`, `version`, `status`, `superseded_by`, `path` |
| `DocType` | `code`, `label` |
| `Classification` | `letter`, `level_name` |

**Edges**

| Edge | From → To | Meaning |
| --- | --- | --- |
| `CONTAINS` | Directory → Document | Directory holds this document |
| `VERSION_OF` | Document → Document | This document is a later version of another |
| `TYPE` | Document → DocType | Document belongs to this type |
| `CLASSIFIED_AS` | Document → Classification | Document carries this classification |
| `SUPERSEDES` | Document → Document | This document replaces another |
| `RECLASSIFIED_FROM` | Document → Document | This document originated from a reclassification of another |

## Registry Compliance

All new directories and documents must follow this specification. Registry files must track:

- Next available directory ID (`DDDD`)
- Next version number per document, per directory
- Current status of each document
- Classification of each directory and document
- Export restrictions based on classification rules (see Registry Export Rules)
- Reclassification lineage
- Supersession relationships
